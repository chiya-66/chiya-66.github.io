命令注入和业务逻辑

命令注入漏洞

一、原理

原理： 命令注入（Command Injection）是指 Web
应用在调用系统命令时（如
exec、system、shell_exec、passthru、反引号），接收了用户输入并直接拼接到命令字符串中，攻击者通过插入特殊字符（如
;, |, &, $()）来执行额外的系统命令。

命令注入漏洞就是指：系统在接收到用户输入后，没有经过充分的验证和过滤，并不区分哪些指令是安全的，哪些是恶意的，直接传递给底层命令执行环境,从而导致攻击者能够插入恶意命令并执行。

命令注入的成因

1.对用户的输入过滤的不彻底

即使开发者对一些特殊字符（如 ; |
&&）做了过滤，但这些过滤是不完整的，可能会遗漏一些特殊的字符，比如 \n
$() ` || ；并且由于windows和 linux
的命令语法不同，可能也会因未针对多平台适配，导致防护失败。

2.信任外部数据源

即使数据来自数据库、文件或第三方接口，若也未经验证直接拼接到命令中，仍可能触发注入。类似二次注入

3.使用危险函数或API

对于直接调用系统命令函数，如PHP中的exec() system()
；Python中的os.system()；Node.js中的child_process.exec() 等函数

权限配置不当

如果应用程序的权限过高，注入的命令也会更具危险性

命令注入漏洞的利用

示例（PHP）：

php

$ip = $_GET['ip'];

system("ping -c 4 " . $ip);//

正常：ip=127.0.0.1// 恶意：ip=127.0.0.1; cat /etc/passwd

正常输入 127.0.0.1 → 执行 ping -c 4 127.0.0.1。攻击输入 127.0.0.1; cat
/flag → 实际执行两条命令：ping -c 4 127.0.0.1 和 cat /flag

常用拼接符：

+—————–+—————————-+—————–+——————+
| 符号 | 含义 | 示例 | 结果 |
+—————–+—————————-+—————–+——————+
| ; | 顺序执行，不管前一句成败 | ls ; cat flag | 执行 |
| | | | ls，然后执行 cat |
+—————–+—————————-+—————–+——————+
| | | 将前命令输出作为后命令输入 | ls | grep flag | 筛选输出 |
| | | | |
| 管道 | | | |
+—————–+—————————-+—————–+——————+
| `cmd` | 执行命令并返回结果（相当于 | `cat flag` | 直接输出文件内容 |
| | $() | | |
| 反引号 | | | |
| | ） | | |
+—————–+—————————-+—————–+——————+

利用技巧

某些场景下需要闭合原有命令：比如命令是 ping -c 4
$_GET['ip']，我们可以传入 127.0.0.1 && cat /flag 或 127.0.0.1 |
cat /flag。

业务逻辑漏洞

一、原理

业务逻辑漏洞是指因业务流程设计不严谨、权限控制缺失、参数校验不足等设计层面问题，导致攻击者可绕过正常业务逻辑，实现未授权操作（如越权访问、密码重置、篡改交易金额）的安全漏洞，属于
“设计漏洞” 而非 “代码实现漏洞”。

二、几类核心漏洞

1. 绕过验证类漏洞

（1）弱口令漏洞

定义：易被猜测或破解的账号密码（如简单数字、个人信息关联密码），攻击者可直接登录或通过简单枚举获取权限。

常见弱口令类型：

简单字符组合：123456、666666、abc123；

个人信息关联：身份证后 6 位、姓名首字母 + 生日（如wangwei1999）；

键盘顺序：1qaz2wsx、2580（手机键盘中间行）；

默认口令：系统 /
设备出厂默认密码（如admin@123）、企业统一初始密码（员工未修改）

（2）暴力破解漏洞

**定义：**攻击者通过自动化工具（如 BP 的 Intruder
模块）穷举账号密码，利用验证机制不完善获取权限。

漏洞成因（满足任一即可）：

无验证码或验证码仅前端验证；

验证码不过期（后端验证但可重复使用）；

无账号锁定机制（输错多次仍可继续尝试）；

错误提示过于详细（如 “用户名不存在””密码错误”，可枚举有效用户名）；

短信验证码过短（＜6 位）、无发送间隔限制。

特殊形式：

撞库攻击：

原理：利用 A 平台泄露的账号密码，批量尝试登录 B
平台（依赖用户在多平台使用相同账号密码）；

特点：绕过验证码、锁定机制等防护，成功率高于普通暴力破解。

实操步骤（BP 爆破示例）：

打开 BP，拦截登录请求，发送至 Intruder 模块；

标记账号、密码参数为 Payload 位置；

加载字典（用户名字典 + 密码字典），选择爆破模式（如
“集群炸弹模式”，账号与密码一一对应）；

执行爆破，通过响应包长度差异（登录成功与失败的响应长度不同）筛选有效账号密码。

越权访问类漏洞

指攻击者突破网站的权限控制机制，访问或操作超出自身权限的资源，分为水平越权和垂直越权两类

（1）水平越权

**定义：**同权限用户访问其他用户的独有资源（如学生 A 查看学生 B
的成绩）。

**核心原理：**权限控制仅依赖前端传递的身份标识（如用户
ID、订单号），未在后端校验该标识与当前登录用户的关联性。

常见实操场景：

场景 1：基于身份标识（用户 ID / 用户名）；

示例：登录用户lucy后，访问个人信息的 URL
为http://xxx.com/user?name=lucy，将name改为lily，即可查看lily的个人信息；

场景 2：基于订单号；

示例：电商平台订单号为连续数字（如14768），遍历订单号14769、14770，可查看其他用户的订单信息（含提货码、收货地址）；

场景 3：基于文件名 / 参数；

示例：文件访问 URL
为http://xxx.com/file?id=2&type=1，修改type=2、id=3，可查看他人的营业执照、注册资料。

（2）垂直越权

**定义：**低权限用户访问高权限用户的资源（如普通用户添加管理员账号）。

常见实操场景：

场景 1：基于 Cookie/Session；

示例：锐捷路由器游客账号登录后，抓包发现 Cookie
值为user=guest，将其改为user=admin，获得管理员权限（可修改路由器配置）；

场景 2：基于高权限操作链接；

示例：抓包获取管理员添加用户的请求包（http://xxx.com/admin/addUser），使用普通用户的
Cookie 替换管理员 Cookie，提交请求，成功添加新用户。

常见越权参数：

admin=0 → 改为 1

role=user → 改为 admin

user_id=123 → 改为 124（水平越权查看他人数据）

修改方法：

  • Burp Suite 拦截请求，直接修改 Cookie 或 GET/POST 参数

  • 浏览器 F12 → 存储 → Cookies → 编辑值并刷新

测试思路：看到 Cookie 里有 0、false、user，尝试改成
1、true、admin，看是否绕过权限限制

3.交易类漏洞

指攻击者利用交易流程设计缺陷，篡改关键参数或绕过流程校验，获取经济利益，核心发生在电商、支付、积分兑换等场景

1. 核心成因

客户端传递的交易参数（金额、数量、订单状态）未在服务端严格校验，仅依赖前端数据，导致攻击者可任意篡改。

2. 三大细分类型

（1）参数篡改

定义：篡改交易关键参数（金额、数量），实现低价购买、虚假充值等；

细分场景：

篡改金额：将手机单价3000改为0.01，支付 0.01 元购买手机；

零数逻辑：将域名注册费关联参数1改为0，实现 0 元注册；

负数逻辑：支付时将金额20改为-30，导致账户余额增加（服务端执行余额-(-30)=余额+30）。

实操示例（酒店团购金额篡改）：

酒店团购页面显示 “两晚总价 150
元”，点击支付，抓包获取请求体（price=85&total=150）；

将price改为0.05、total改为0.1，提交请求；

服务端未校验参数真实性，最终支付 0.1 元完成团购。

类型 2：重放攻击

定义：抓取正常交易 /
活动的请求包，重复发送，实现重复获利（如重复领取积分、流量）；

示例：新浪微博抽奖送流量活动，抓包获取领取流量的请求包，使用 BP 的
Repeater 模块反复发送，无限领取流量。

类型 3：流程漏洞

定义：利用交易流程（如下单、退货、优惠券使用）的逻辑缺陷获利；

示例：购买主商品（3 元）+ 免费赠品（原价 10
元），下单后申请退货，服务端未区分主商品与赠品，将 13 元全额退款（多退
10 元）。
