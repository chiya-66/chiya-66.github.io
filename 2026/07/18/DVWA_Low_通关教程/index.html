一、DVWA 简介与环境准备

1.1 什么是 DVWA？

DVWA（Damn Vulnerable Web Application）是一个故意设计得漏洞百出的 Web 应用程序。它的目的不是给你做一个好网站，而是给你一个合法的靶场，让你练习如何发现和利用 Web 漏洞。

打个比方：DVWA 就像是一个”拆弹训练场”——里面放置了各种不同类型的”炸弹”（漏洞），你在里面练习拆弹，练好了以后才能在真实场景中保护系统。

1.2 安全级别说明

DVWA 有四个安全级别：

级别 说明
Low 毫无防护，代码直接把用户输入传给后端处理
Medium 做了一些简单的过滤
High 做了较严格的防护
Impossible 使用了安全编码的最佳实践，基本无法攻破

本教程使用 Low 级别，因为在这个级别下，代码没有任何防护措施，非常适合零基础同学理解漏洞的本质原理。

1.3 环境准备

  1. 确保 DVWA 已经启动并能正常访问
  2. 在浏览器中打开 DVWA 页面
  3. 使用默认账号登录：用户名 admin，密码 password
  4. 登录后，点击左侧的 DVWA Security，将安全级别设置为 low，然后点击 Submit

提示：每次切换关卡后，最好确认安全级别仍然是 low，因为某些操作可能会重置它。

1.4 几个必须理解的前置概念

在开始之前，你需要了解几个基础概念：

前端与后端

  • 前端：你在浏览器里看到的东西——按钮、输入框、页面排版。前端代码（HTML/CSS/JavaScript）运行在你的浏览器里。
  • 后端：服务器上运行的程序——处理数据、读写数据库、执行业务逻辑。后端代码（PHP/Python/Java 等）运行在服务器上。
  • 漏洞通常出现在后端没有正确验证和处理前端传来的数据。

HTTP 请求

  • 当你在网页上填写表单并点击提交时，浏览器会向服务器发送一个 HTTP 请求。
  • 这个请求包含了你输入的所有数据。
  • 攻击的核心思路就是：在发送给服务器的数据中夹带”恶意内容”。

数据库

  • 网站的数据（用户名、密码、文章内容等）存储在数据库中。
  • 后端程序通过 SQL 语言来操作数据库（增删改查）。
  • 如果后端直接把用户输入拼接到 SQL 语句中，就会产生 SQL 注入漏洞。

二、Brute Force（暴力破解）

2.1 这个漏洞是什么？

暴力破解，简单来说就是不停地尝试不同的用户名和密码组合，直到猜对为止。

就像你忘了自己行李箱的密码锁，就从 000 开始一个一个试，试到 999 总能打开。网站登录也是一样——如果网站不限制尝试次数，攻击者就可以用程序自动尝试成千上万个密码。

2.3 手动尝试

  1. 点击左侧菜单的 Brute Force
  2. 你会看到一个登录表单，有用户名和密码输入框
  3. 先手动试一下：输入 admin / password，点击 Login
  4. 登录成功后会显示用户名和密码

2.4 使用 Burp Suite 进行暴力破解

虽然手动也能试，但要试几百个密码就不现实了。我们需要一个工具来自动化这个过程。

Burp Suite 是一款常用的 Web 安全测试工具，它的核心功能之一就是拦截和修改浏览器与服务器之间的通信。

第一步：配置 Burp Suite 代理

  1. 打开 Burp Suite
  2. 进入 Proxy 选项卡 → Options → 确认代理监听端口为 8080
  3. 在浏览器中设置代理为 127.0.0.1:8080

第二步：抓取登录请求

  1. 在 DVWA 的 Brute Force 页面，随意输入用户名和密码（比如 admin/123456）
  2. 点击 Login
  3. 回到 Burp Suite，在 Proxy → HTTP history 中找到这个登录请求
  4. 右键该请求 → Send to Intruder（发送到入侵模块）

第三步：配置攻击参数

  1. 切换到 Intruder 选项卡
  2. 在 Positions 标签中，你会看到请求内容
  3. 找到 password=123456 这部分
  4. 在 123456 两边点击 Add § 按钮，使其变成 password=§123456§
    • § 符号标记了”攻击位置”，Burp 会自动替换这个位置的值
  5. 在 Payloads 标签中：
    • Payload type 选择 Simple list
    • 在下方文本框中输入常见密码（每行一个），比如：
  6. 点击 Start attack 开始攻击

第四步：分析结果

  • 攻击完成后会弹出一个窗口，显示每次尝试的结果
  • 关注 Status 列（HTTP 状态码）和 Length 列（响应长度）
  • 找到长度明显不同的那行——通常成功登录的页面和失败页面的长度不同
  • 点击该行，在右侧查看响应内容，确认是否登录成功

2.5 知识点总结

概念 解释
暴力破解 尝试所有可能的密码组合直到猜中
Burp Suite 拦截浏览器和服务器之间通信的工具
代理（Proxy） 让浏览器的流量先经过 Burp Suite，从而可以查看和修改
Intruder Burp Suite 的自动化攻击模块
Payload 攻击载荷，即要尝试的密码列表

2.6 防御方法

  • 限制登录尝试次数：连续失败 N 次后锁定账户或增加验证码
  • 使用强密码：长而复杂的密码让暴力破解变得不现实
  • 添加验证码：区分人类和自动化程序
  • 账号锁定机制：多次失败后临时锁定

三、Command Injection（命令注入）

3.1 这个漏洞是什么？

命令注入是指攻击者通过在用户输入中嵌入操作系统命令，让服务器执行了本不该执行的命令。

打个比方：一个网站有一个功能是”查询 IP 地址”，你输入一个 IP，服务器会执行 ping 你的IP 这个系统命令。但如果网站没有做检查，你输入 127.0.0.1; ls，服务器实际执行的就变成了：

ls 是 Linux 列出文件列表的命令。服务器不仅 ping 了 IP，还把当前目录的文件列表展示了出来——这就是命令注入。

3.2 前置知识：Linux 常用命令

在开始之前，你需要知道几个基本的 Linux 命令：

命令 作用
ls 列出当前目录下的文件和文件夹
cat 文件名 查看文件内容
pwd 显示当前所在目录
whoami 显示当前用户
ifconfig 或 ip a 查看网络配置
id 显示用户ID和组ID
uname -a 显示系统信息

3.3 前置知识：命令连接符

命令注入的核心在于命令连接符，它们允许你在一个命令后面追加另一个命令：

符号 含义 举例
; 顺序执行，不管前面成功失败 命令1; 命令2 → 先执行1，再执行2
&& 前面成功才执行后面 命令1 && 命令2 → 1成功才执行2
| 前面命令的输出作为后面命令的输入（管道） ls | grep txt → 列出包含txt的文件
` `
` （反引号） 执行反引号内的命令，把输出插入到原命令中 echo whoami`` → 显示当前用户名
$() 和反引号类似，执行括号内命令 echo $(whoami)

四、CSRF（跨站请求伪造）

4.1 这个漏洞是什么？

CSRF（Cross-Site Request Forgery），跨站请求伪造。

简单解释：攻击者构造一个恶意网页，当你访问这个网页时，它会代替你向目标网站发送请求。因为你的浏览器里保存着登录状态（Cookie），服务器会以为是你本人在操作。

打个比方：有人伪造了一封有你签名的信件，寄给银行要求转账。银行看到签名就信以为真，其实信不是你写的。

4.2 前置知识：Cookie 和会话（Session）

概念 解释
Cookie 服务器发送给浏览器并存储的小数据块，用于标识用户身份
Session 服务器端存储的用户会话信息
登录状态 你登录后，浏览器会自动在后续请求中带上 Cookie，服务器据此识别你

正是因为浏览器会自动带上 Cookie，所以 CSRF 攻击才能成功——恶意网页发出的请求也会带上你的 Cookie。

4.5 知识点总结

概念 解释
CSRF 利用用户的登录状态，伪造请求代替用户操作
Cookie 浏览器自动携带的身份凭证，是 CSRF 攻击成功的关键
隐藏表单 攻击者用不可见的表单自动提交恶意请求
CSRF Token 服务器生成的一次性令牌，用于验证请求来源的合法性

4.6 防御方法

  • CSRF Token：每次表单提交时携带一个服务器生成的随机令牌，服务器验证令牌是否有效
  • Referer 检查：检查请求来源页面是否是合法页面
  • 关键操作二次验证：修改密码等操作要求输入原密码
  • SameSite Cookie：设置 Cookie 的 SameSite 属性为 Strict 或 Lax

五、File Inclusion（文件包含）

5.1 这个漏洞是什么？

文件包含漏洞是指攻击者可以控制文件路径，让服务器包含并执行任意文件。

在 PHP 中，有两个函数可以从外部文件加载代码：

函数 含义
include() 包含并执行指定文件，如果文件不存在只产生警告
require() 包含并执行指定文件，如果文件不存在产生致命错误

如果文件路径是用户可控的，攻击者就能让服务器加载恶意文件。

5.2 前置知识：本地文件包含 vs 远程文件包含

  • LFI（Local File Inclusion，本地文件包含）：包含服务器上已存在的文件
  • RFI（Remote File Inclusion，远程文件包含）：包含互联网上其他服务器上的文件

RFI 的危害更大，因为攻击者可以完全控制被包含文件的内容。

六、File Upload（文件上传）

6.1 这个漏洞是什么？

文件上传漏洞是指网站允许用户上传文件，但没有对文件类型进行严格验证，导致攻击者可以上传恶意文件（通常是 Webshell），然后通过浏览器访问该文件来控制服务器。

打个比方：一个网站允许你上传头像图片，但你上传了一个伪装成图片的程序文件，服务器没有识别出来，把它当普通文件存了下来。然后你通过浏览器访问这个文件，它就作为程序运行了——你的恶意代码就在服务器上执行了。

6.2 前置知识：什么是 Webshell？

Webshell 就是一个可以通过浏览器访问的脚本文件，它提供了控制服务器的功能。

6.4 漏洞原理（源码分析）

逐行解读：

  1. $_FILES[ 'uploaded' ][ 'name' ] — 获取上传文件的原始文件名

文件后缀 文件名的扩展名，如 .php .jpg

6.6 防御方法

  • 白名单后缀检查：只允许上传图片后缀（.jpg、.png、.gif）
  • 检查文件内容（Magic Bytes）：验证文件头部的魔数，确保是真正的图片
  • 重命名文件：使用随机生成的文件名，不使用用户上传的原始文件名
  • 上传目录禁止执行：设置上传目录不可执行 PHP 等脚本
  • 文件大小限制：限制上传文件的大小

八、SQL Injection（Blind）（盲注）

8.1 这个漏洞是什么？

盲注是 SQL 注入的一种特殊形式。区别在于：

  • 普通 SQL 注入：查询结果会直接显示在页面上
  • 盲注：查询结果不会显示在页面上，但攻击者可以通过页面的其他反应（比如”有结果”vs”无结果”，或”响应快”vs”响应慢”）来逐个字符地猜出数据

就像你问一个人”密码第一位是不是 a？”，他只会回答”是”或”不是”，你通过不断提问最终猜出完整密码。

8.2 盲注的两种类型

类型 原理 特点
布尔盲注 根据页面返回 True/False 两种不同状态来判断 页面有明确的两种不同反应
时间盲注 通过 SLEEP() 函数让数据库延迟响应，根据响应时间判断 页面没有明显不同反应

8.3 动手实践

第一步：观察页面行为

  1. 点击左侧的 SQL Injection (Blind)

  3. 输入 999，点击 Submit — 页面显示 “User ID is MISSING from the database”

可以看到，页面只有两种状态：存在 / 不存在。这就是布尔盲注。

8.5 知识点总结

概念 解释
布尔盲注 通过页面 True/False 两种状态逐字符猜数据

九、XSS（Reflected）（反射型跨站脚本）

9.1 这个漏洞是什么？

XSS（Cross-Site Scripting），跨站脚本攻击。攻击者向网页中注入恶意 JavaScript 代码，当其他用户浏览该网页时，注入的代码会在用户的浏览器中执行。

反射型 XSS 的特点：

  • 恶意代码不会保存到服务器上
  • 攻击者需要构造一个包含恶意代码的链接，诱导受害者点击
  • 代码通过 URL 参数反射回页面并执行

打个比方：攻击者在一张名片（URL）上写了恶意内容，你打开这个名片时，内容就在你的浏览器里执行了。

9.2 前置知识：JavaScript 基础

代码 作用
alert('XSS') 弹出一个对话框显示 “XSS”
document.cookie 获取当前页面的 Cookie
window.location 获取或修改当前页面的 URL
document.getElementById() 获取页面上的元素

在 XSS 漏洞验证中，最经典的测试 payload 就是 alert('XSS')——如果弹出了对话框，说明存在 XSS 漏洞。

<script> 标签 HTML 中嵌入 JavaScript 的标签

9.6 防御方法

  • Content Security Policy (CSP)：设置 HTTP 头，限制页面可以加载哪些脚本
  • 输入验证：白名单允许的字符

十、XSS（Stored）（存储型跨站脚本）

10.1 这个漏洞是什么？

存储型 XSS 是 XSS 中危害最大的类型。

与反射型不同，存储型 XSS 的恶意代码会被永久保存到服务器上（通常是数据库中）。每当其他用户访问包含恶意代码的页面时，代码就会自动执行。

打个比方：反射型 XSS 像是在传纸条——纸条上写了恶意内容，你看完就没了。存储型 XSS 像是在黑板上写字——所有走进教室的人都能看到。

第三步：理解危害

想象一下：如果攻击者在一个论坛的帖子里注入了窃取 Cookie 的 JavaScript 代码，那么每个浏览这个帖子的人的 Cookie 都会被窃取，攻击者就能冒充他们的身份登录。

注意看：代码使用了 mysqli_real_escape_string() 来防止 SQL 注入（这是好事！），但是没有对输出进行 HTML 转义。所以 <script> 标签被原样存入数据库，读取显示时也没有被转义，从而导致了 XSS。

这告诉我们一个重要道理：防御 SQL 注入和防御 XSS 是两件不同的事，需要分别处理。

10.4 知识点总结

概念 解释
存储型 XSS 恶意代码被保存到服务器，每次访问都会触发
危害最大 因为影响所有访问该页面的用户
输入过滤 vs 输出转义 输入过滤防 SQL 注入，输出转义防 XSS，两者缺一不可

10.5 防御方法

  • 输出时进行 HTML 转义：使用 htmlspecialchars() 函数将特殊字符转义
  • 富文本过滤：如果需要支持富文本，使用白名单策略只允许安全的 HTML 标签和属性

十一、XSS（DOM）（DOM 型跨站脚本）

11.1 这个漏洞是什么？

DOM 型 XSS 与前两种 XSS 的区别在于：

  • 反射型和存储型的恶意代码会经过服务器处理
  • DOM 型 XSS 完全在客户端（浏览器） 发生，恶意代码不会发送到服务器

DOM（Document Object Model）是浏览器将 HTML 文档解析后生成的树形结构。JavaScript 可以通过 DOM API 来修改页面内容。如果 JavaScript 代码直接使用了不受信任的输入（如 URL 参数）来修改 DOM，就可能产生 DOM 型 XSS。

打个比方：前两种 XSS 是厨师（服务器）在菜里下了毒，DOM XSS 是你自己（浏览器）拿着不明食材做菜时中了毒。

11.2 前置知识：DOM 操作

JavaScript 代码 作用
document.write() 向页面写入内容
document.getElementById('id').innerHTML 获取或设置元素的 HTML 内容
document.getElementById('id').src 设置元素的来源（如图片地址）
location.hash 获取 URL 中 # 后面的部分
window.location.search 获取 URL 中 ? 后面的查询参数

十二、总结与学习建议

12.1 DVWA Low 级别所有漏洞一览

序号 漏洞名称 漏洞类型 核心原理 危害等级
1 Brute Force 认证类 无限制的登录尝试 中
2 Command Injection 代码执行类 用户输入被拼入系统命令 极高
3 CSRF 认证类 伪造用户请求 高
4 File Inclusion 代码执行类 用户控制被包含的文件路径 极高
5 File Upload 代码执行类 上传恶意脚本文件 极高
6 SQL Injection 数据泄露类 用户输入被拼入 SQL 语句 极高
7 SQL Injection (Blind) 数据泄露类 通过布尔/时间差异猜数据 高
8 XSS (Reflected) 客户端攻击 恶意 JS 通过 URL 反射回页面 中
9 XSS (Stored) 客户端攻击 恶意 JS 被保存到服务器 高
10 XSS (DOM) 客户端攻击 前端 JS 代码不安全处理输入 中

12.2 所有漏洞的共同根因

尽管这 10 个漏洞的表现形式各不相同，但它们有一个共同的根因：

后端代码（或前端代码）没有对用户输入进行充分的验证和过滤，直接信任并使用了用户输入。

这被称为 “永远不要信任用户输入”（Never Trust User Input） 原则——这是 Web 安全的第一法则。

12.3 学习路线建议

  4. 学习使用工具：Burp Suite、SQLMap、Nmap、OWASP ZAP

    • WebGoat：OWASP 出品的教学靶场
    • Pikachu：国内的中文靶场，适合初学者
